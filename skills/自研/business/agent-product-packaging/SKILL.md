# 把 AI Agent 能力打包成可交付给客户的产品

## 何时用

- 合作方说「先打个样」「做个框架，我拿给客户看」「做个安装包，用户一键装」
- 要把自己的技能包 / 工作流交付给第三方，或谈「后期个性化定制」「售后」怎么收费
- 客户问「这个能不能全自动」「能不能帮我发布」「能不能代运营」
- 判断拿开源工具（Hermes 等）当交付底座合不合法、包里要放什么

## 铁律（先过这五条，再动手）

1. **打样不是免费的默认动作。** 打样前先问清四件事：给不给钱、交付到什么程度、他拿去做哪些用途（只给客户演示 / 当教材 / 转卖 / 署谁的名）、打完样之后接什么。四问答不上来就不开工——样板是**可复制资产**，白送一次等于把核心东西交出去。
2. **定制必须落成「配置」，不能落成「改代码」。** 客户填表 → 按参数生成他的实例，这才叫可复制；每个客户都去改代码，就是不可复制的体力活，售后永远做不完，「带三个是手艺、带三十个才是生意」的分水岭就在这里。参数化体系是对方抄不走的东西，也是我方在合作里不可替代的地方。
3. **两张单子：交付清单 + 不做清单。** 不做清单比交付清单更重要——不代写内容、不代运营、不承诺涨粉与收益、不担平台封号。客户（尤其散户）会一步步把「帮我配个流程」挪成「帮我把号做起来」，每一步都像顺手；不划这条线，客户就会往他舒服的方向替你划。想滑坡可以，做成单独报价的包（如「月度陪跑」「代运营」），他要么付钱要么缩回去。
4. **客户侧的资质要写进合同，并且直接决定功能档位。** 平台开发者权限（企业主体＋审核）、账号认证主体、支付商户号、对公账户、营业执照——出不来，某些功能就只能停在人工档，这不是技术问题。
5. **交付物一旦落到客户机器上就是可见可拷的**（技能＝调好的提示词与模板）。交付前先定：授权范围、署名、能不能转卖/教学、后续更新怎么给。

## 产品形态阶梯（按顺序交付，别一步跳到大而全）

1. **技能包 + 双击安装脚本** —— 当天可演示，先拿这个给合作方看，别先做界面。
2. **套一层安装界面**（Windows 上 Inno Setup，免费）做成 `.exe`：有下一步、有进度条，这就是合作方嘴里「一个安装包」的样子。
3. **首次运行向导**：一次性表单（填 API key、选行业方向、选平台）→ 自动生成他的个性化配置。个性化定制在这一步交付完成，不需要远程动手。

包内构成与依赖处理见 `references/hermes-packaging-and-license.md`（官方安装器已把 Python/Node/ffmpeg/便携 Git 全包了，**不要自己攒运行环境**）。
客户端交付框架（五层骨架、三块标准件、定制件、快速上手四件套、客户侧账户/API 清单、生图引擎接法）见 `references/client-delivery-framework.md`。

## 售后 = 技能包更新（这是回头钱，要提前设计）

基础版装完，之后每期给一份「技能包更新」（新平台适配、新模板、新玩法、修 bug）。同一份更新发给一百个客户成本一样——这就是把「个性化定制 / 售后」做成了可复制产品。谈合作时把这层单独拎出来：交付物＝技能包，收费点＝更新节奏。

## 回答「这条能做吗 / 能全自动吗」的拆法

把一句话需求拆成环，逐环判：找信息 → 整理成清单 → 改写成各平台版本 → 配图 → 发布。前几环能做，最后一环（点发布）通常不能全自动。

- 标准口径：**自动化能吃到八成**（找信息、写各平台文案、配图、打成发布包），最后一环留人或做半自动，缺的是资质不是技术。
- 发布环节的三档现实、逐平台接口边界、以及公众号草稿箱这个例外，见 `collaboration-proposal-review` 技能的 `references/platform-publishing-api-reality.md`。
- 交付给客户时优先卖「八成无人」——那八成正是他一天干不完的活。
- **对外口径只写到能交付的那一档**：说「支持提供 API 的模型，装的时候填自己的 key」，不说「什么账号都能接」——只有提供 API 的模型接得进来；只有网页版账号的（网页版生图、剪辑/设计类会员）接不进来，除非模拟浏览器点击（违规＋封号，不做）。话说过头，交付时就变成我方的问题。

## 落地顺序（一次会话内怎么推）

1. 先给使用者一张清单（产品形态 + 包内构成 + 先做哪步）让他拍板，**不要擅自开工大工程**。
2. **分清「讨论」与「执行」**：使用者讲思路、说「举个例子」「如果我说……」时是在描述场景，不是在派活——不要顺手去查本机、建文件、写技能，先把方案说清并等他确认（他会打断：「我只是举例子，并不是让你真的跑」）。同理，他要「列个清单 / 立个框架」时要的是**通用骨架**，不是这台机器的体检报告；他说「等有客户了再抠」＝停止深挖的信号。
3. 工作目录建在 D 盘独立目录（如 `D:\opc-lab`），不碰使用者现用的 Hermes 环境；技能包先在干净目录/独立 profile 里验证再给客户。
4. 实测优先于描述：能打开的实物（样张、跑起来的界面、打好包的发布件）比文档有说服力，也是回答「你凭什么能做」的唯一有效证据。
5. 每步做完报一句结果；长耗时安装（几百兆以上的依赖）开跑前先说一句在装什么。

## 用户偏好（必遵）

- 输出用 **txt**（不用 md），放 `桌面\我的小项目\<任务名>\`，回复里给绝对路径；生成/安装优先放 D 盘。
- **不瞎编**：许可、平台接口、价格、政策类结论要先查证或实测，写清「已核实」还是「需实测」，不凭记忆断言。
- **不会的直接写「不会」**，不包装成「分工不合算」；对外要有自己的方案，不当别人的执行方。
- 先小活验证：用「3 天可交付的小活 + 结一次账」验合作方掏钱的意愿和沟通效率，再谈长期。
- 追加记录类文件（对接记录/日志）用 patch 追加，`write_file` 是整体覆盖会吃掉前面内容。

## 常见坑

- **别自己攒运行环境**：官方安装器已经把 Python / Node / ripgrep / ffmpeg / 便携 Git 装齐，而且不干扰客户机器上原有的东西；自己攒既重复劳动又更容易坏。
- **只演示不绑定**：演示物料给出去后就收不回来，条件（钱、范围、用途）要在给之前谈。
- **把「安装包」当终点**：一次性的安装费不是生意，复利在更新与陪跑。
- **别把「他名气大 / 客户多」当回报**：他获客、你干活的结构里，要主动提分成或按单结算的口子，等他「有单了再说」就等于没有。
- **开源底座的许可要在开工前查原文**（LICENSE 文件，不是二手转述），见 `references/hermes-packaging-and-license.md`。
