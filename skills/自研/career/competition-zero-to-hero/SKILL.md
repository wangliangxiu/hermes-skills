# 零基础参赛全流程 Skill

## Overview

当用户说"想参加XXX比赛但完全没经验"时使用本技能。覆盖从组队、定方向、写商业计划书到落地的全流程。

触发词：比赛、参赛、青年科技大赛、创新创业大赛、挑战杯、互联网+、黑客松、hackathon、buildathon、奖金、提交截止

使用者丢来一个比赛/活动链接（常只说"来活了"）时：先把链接内容读全（活动页 + 官方手册），再按下面的流程。链接读不到就见第一步的"登录墙"条。

## 使用者画像

- 使用者，河南理工大学土木工程本科，中铁十五局6年，本地日报社
- 求职AI公司（增长/内容运营/AI应用方向，目标月之暗面等，非纯编程岗）
- 零比赛经验，但有工程行业+AI Agent+媒体运营复合背景
- 使用Hermes Agent（DeepSeek API），偏好中文沟通
- 有BIM建模能力的朋友（国企机械设备厂）
- 两个人都可以全职投入

## 通用流程

### 第一步：了解比赛信息
- 查找比赛官方通知（主办方、赛道、组别、时间节点、奖励政策）
- 判断用户适合哪个赛道/组别
- 种子组 vs 成长组的区别：种子组不需要注册公司
- **官方手册常在登录墙里**（飞书 my.feishu.cn/wiki、Notion、语雀、腾讯文档、Google Docs）：抓取只拿到空壳 HTML（正文一个字都没有，只有"登录/集群/私有部署"这类导航词），文档接口回的也是 "Login Required"。**别反复试接口、别换路由重试**——登录墙内的文档任何存档/阅读器都渲染不出来。直接请使用者复制正文贴过来，或导出 PDF/Word 发本地路径（他本来就在登录态，30 秒的事）。
- **微信公众号文章（mp.weixin.qq.com）非微信环境读不全**：正文由 JS 二次加载，换微信 UA、走阅读器都一样，只有 `<meta name="description">` 和 `window.cgiDataNew.desc` 里的标题/公众号/发布时间/整段摘要拿得到（摘要常含章节结构与要点清单）。先把摘要读给使用者，再请他把正文粘过来；他一段一段粘的时候**不要每条都汇报**，闷头收集，粘完一次性出文件。
- **时间节点经常不在手册里**：主办方把时间线表格嵌在飞书文档里，外部预览显示"暂时无法在飞书文档外展示此内容"。截止时间必须让使用者在官方群/主办处问准后写进计划，别卡截止。
- **报名入口别搞错**：主办后台地址（如 luma.com/event/manage/...）不是公开入口，公开报名页是 luma.com/<短码>，形式多是"Request to Join + 主办审批"。

### 第二步：盘点家底
- 用户已有的技能、资源、人脉、数据
- 团队成员各自擅长的方向
- 可全职/业余投入
- 列出人员档案（建议做成Excel表格，横向表头=成员，纵向=信息项）

### 第三步：找方向  
- 结合用户背景brainstorm可能的项目方向  
- **关键原则：先落地再做比赛** — 有实物/数据比纯PPT更有说服力  
- 用户偏好真实可用的产品方案，不要纸上谈兵

### 第三步.五：项目论证与筛选（新增）
- 如果有多个备选方向，用 **项目筛选论证表**（参见 references/项目筛选论证表-模板.md）进行系统对比
- 表结构：项目赛道 | 项目内容 | 项目优势 | 项目痛点 | 能否克服 | 克服痛点需要哪些
- 6列全部如实填写后，自然能看出哪个方向更靠谱
- **原则**：优势要写真实已拥有的资源/数据，不编造；痛点要诚实；不能克服的就直接淘汰

### 第四步：技术可行性评估
- 团队成员技术栈能否支撑这个方向？
- 需要什么外部资源（数据、设备、接口）？
- 有没有现成的工程场景可以测试验证？

### 第五步：商业计划书（BP）

#### BP框架（8章结构）
```
一、执行摘要
二、市场分析（2.1行业背景与痛点 / 2.2市场规模TAM/SAM/SOM / 2.3SWOT分析 / 2.4竞品分析）
三、产品方案（3.1产品概述 / 3.2核心功能 / 3.3技术架构 / 3.4技术壁垒）
四、商业模式（4.1价值主张 / 4.2收入模式 / 4.3成本结构 / 4.4盈利预测）
五、运营计划（5.1里程碑规划 / 5.2推广策略）
六、团队介绍（6.1核心成员 / 6.2顾问导师）
七、财务预测（7.1 3年营收预测 / 7.2资金用途）
八、风险与对策（8.1技术风险 / 8.2市场风险 / 8.3管理风险）
附录（产品截图 / 调研数据 / 简历 / 支撑材料）
```

#### 角色分工（6人制团队）
| 角色 | 负责的BP章节 |
|:---|:---|
| 队长 | 执行摘要、SWOT、团队信息、里程碑、风险对策 |
| 技术 | 产品功能、技术架构、壁垒、开发进度 |
| 商业 | 市场调研、TAM/SAM/SOM、竞品、收入模式、财务预测 |
| 设计 | 产品界面设计、产品截图、团队形象照、PPT美化 |
| 路演 | 路演稿（8分钟）、Q&A题库（20+问题） |
| 文案 | BP润色、文档整理、附件材料 |

#### 术语速查（BP常见字母缩写）
- **TAM** = Total Addressable Market（总可用市场）— 整个蛋糕多大
- **SAM** = Serviceable Addressable Market（可服务市场）— 你够得着的蛋糕
- **SOM** = Serviceable Obtainable Market（可获得市场）— 第一口能吃下的
- **SWOT** = Strengths/Weaknesses/Opportunities/Threats（优劣势分析）
- **MVP** = Minimum Viable Product（最小可行产品）— 最少功能先做出来验证
- **BP** = Business Plan（商业计划书）
- **Demo** = Demonstration（演示/样机）— 现场展示产品
- **Q&A** = Questions and Answers（问答环节）— 路演完评委提问

#### BP填写铁律（实战教训 2026.8）
- 只填有真实产出支撑的内容（原型/文档/测试结果），不确定的数据标【待补】，绝不编数字——使用者写作铁律：打死不许瞎编
- 团队、市场、财务数字以官方规则/真实调研为准，不引用自拟文档里的数字
- 小团队对外材料**不点名对比大厂**（"不碰瓷"），只讲自己的差异化与价值；对标分析留内部参考，对外一字不提
- Word版BP空白章节标题用**黄色字体**标出（正文+目录一致，如FFC000琥珀黄白底可读），一眼看出待补项；生成文档遇文件被Word占用报PermissionError时存v2新文件名
- 交付流程：txt初稿→使用者确认→按确认意见生成Word（蓝色H1/H2排版，【待补】灰色提示）

#### 报名材料写作（项目简介/团队简介/核心能力）— 实战教训 2026.8
- 各栏字数先问清：项目简介常限60字内；团队简介/核心能力常限50-800字。动笔前确认每栏上限
- **团队简介/核心能力不写成员分工**（"谁负责什么"）——写团队整体能干什么、基于本项目落地能做成什么。评委看能力与成果，不看成员履历
- **AI是主线不是凑数项**：使用者求职AI公司，AI含量（大模型Agent/知识库问答/AI辅助决策/围岩识别）必须放核心能力前两条，工程能力殿后；绝不要把AI写成最后一条"智能化服务"弱项
- 落地导向：写"系统已实现/可做到XXX"（参数化布孔、钻孔执行表下发、定位纠偏、施工日志闭环等真实功能），不写规划愿景
- 团队构成（2026.8更新）：4人=使用者(AI/软件)+小伙伴(BIM/硬件)+设备所所长(设备管理/资源)+所里技术人员(现场调试/实测数据)；所长和技术人员只写确定职务与作用，不编个人细节
- 动笔前先 session_search 确认系统真实落地的AI功能（如凿岩台车Agent=知识库问答+参数计算双模式、经验系数全可调；围岩识别/MWD模块），只写真有的，不瞎编能力

#### 组队与招募语（找队友 / 自我介绍）— 实战教训 2026.8
- **动笔前先核实物证据，别替使用者吹**：能力逐条过本机——项目文件夹、`find` 找产物文件、`command -v <cli>` 看装了哪些工具——标成"有实物 / 待他确认 / 没有"三类；只有他口头说过、找不到产物的条目，先问他确认，不写进文案。界面类能力必须把已有截图调出来自己看过（vision_analyze）再下判断，别凭印象夸
- **只写有实物的能力**：招募语里写了自己不熟的东西，队友进来第一句就是"演示一下"，当场穿帮；少写一条比埋个雷强
- **缺什么就写"缺什么"**：写"懂 X"招来的是挑刺的人，写"想找人搭 X"招来的是补位的人（缺合约就写"合约这块想找个人搭"）
- 交付**长短两版**：长版发群做自我介绍（能力清单 → 我在做什么 → 我缺什么 → 一句低门槛收尾如"娱乐为主，不卷"），短版一行能力+一行缺口，用来回复别人的招募帖
- 行业背景按对外材料一贯口径写（如"多年施工经验"，不写年限）；没产物的项目名不当作品写

### 第六步：赛后总结
建议在备战计划Excel中新增一个「赛后总结」Sheet，包含：
1. **成员收获表** — 每人一行：姓名/角色/学到的新技能/最大困难/怎么解决的/印象最深的事
2. **项目关键数据** — 赛道/项目名/比赛结果/评委反馈/遗憾不足
3. **个人成长雷达** — 赛前赛后自评（技术能力/商业思维/团队协作/演讲表达等8项）
4. **最后想说的话** — 每人留一句话纪念

## 黑客松类比赛（Hackathon）

与BP类比赛的关键差别：**不评商业计划，只评能不能跑起来**。硬门槛通常是"必须真部署上线 + 能实操演示 + 代码仓库公开"，PPT 讲故事直接出局。评审维度一般是创新性、与平台技术的相关性、代码完整性、Demo 演示水平，外加一条"方向多元性"（某方向已有项目入选时，会把冷门方向的项目往上提一提）。

### 定方向的策略（决定成败）
- **先问"参加这个比赛图什么"，再出选题**（目标没定就出题=白出，使用者会追问"为什么是这些"）。四种常见目标对应不同选题：①图求职叙事 → 挑贴合他职业方向的赛道（内容/创作者经济/消费支付），让作品和面试故事一条线；②图稳 → 存证/公益类，工作量最小；③图技术含金量 → 官方点名的重点技术方向（x402、AI Agent 支付）；④图圈子曝光 → 挑容易传播、能拉人气票的，与技术难度无关。
- **给候选方向时必须附"为什么是这些"的依据**：对应哪条评审标准、他的差异化在哪、工作量几天。只给结论会被打回。
- **用行业认知做差异化，但别把具体项目硬搬**：多数参赛者是纯技术人，做的都是通用 DeFi/NFT/AI Agent，撞车严重；把真实的行业痛点搬到链上，评审觉得新鲜，"多元性"那条还加分。但**只借"他懂这套业务"，不要把既有的具体项目（如凿岩台车智能系统）搬进调性无关的赛事**——使用者会直接反问"这跟比赛有什么关系"；贴不上就砍掉这条线，别为了用上老本行而凑题。
- **主线上只做一件事**：10 天级的短周期做两条线必崩。技术亮点可以当主线的配件（例：主线是设备数据上链台账，配件是第三方数据服务用 x402 按次付费），但对外只有一个故事。
- **使用者说"全要"（又要稳、又要技术亮点、又要曝光）时不等于做多个项目**：一条主线做扎实，其余目标各自挂上去（曝光=提交后顺手发内容拉人气票；含金量=主线里用上官方点名的技术；叙事=场景别跟他的职业方向打架）。同时把目标间的冲突当面讲清：越新的技术越不稳（含金量 ↔ 稳）、拉票占用开发工期（曝光 ↔ 进度）；"截止前交出一个能真演示的东西"永远是底线，不是可选项。
- 给使用者 **3 个候选方向让他挑**（使用者不喜欢被替他决定），每个写清：痛点、做法、为什么适合他、平台相关性怎么讲、难度。
- **他连着几轮"再想个方式"／"都还可以"＝不是嫌量少，是他心里已有画面**：别继续换汤不换药地加候选（每批换维度：生活场景→技术路线→演示形态），而是停下来反向问他想要的感觉，用四个具体问题把画面抠出来：①这东西干嘛的、给谁用；②打开第一眼屏幕上是什么；③哪一步最爽、最想拿给别人看；④要"生活里真用得上"还是"技术上有东西"。他一旦说出自己的题（哪怕只有一句，如"以财神为背景做发财主题"），就顺着他的想法往下推、逐项三分法评估，不要回头再推自己的候选单。
- **平台相关性要一句话讲得清**：官方反复点名的技术点（如 Avalanche 的亚秒确认/低 gas/L1/ICM/x402）必须能对应到项目里，这正是“相关性”那一项的得分点。
- **单人 + 短周期的选题过滤器**：候选题必须三过——单个闭环（一条链走完，不需要多个子系统互相对接）、演示有画面（三两分钟能看出发生了什么）、一句话讲得清（对外一句话说清是干嘛、给谁用）。过不了的直接砍：功能数量不加分，评委只看那几分钟的演示和那几页材料。
- **创新点靠“反向切入”，不靠堆功能**：先把该方向的主流做法列出来（多半是“让 X 能 Y”），再挑没人做的那条边（“让 X 的 Y 有人管 / 能被验证”）。反向切入一眼可辨地新，工作量往往还更小。
- **Agent 类项目必须把“决策过程”演给人看**：只给结果，评委看不出 AI 在哪；把它的判断一步步显示出来（看了什么 → 决定做什么 → 执行 → 结果），这是“自主性”唯一的证据，也是演示里最抓人的画面；本机已有现成的 loop 骨架可复用。
- **文化主题是差异化富矿，但要防土**：中国传统符号（财神、节气、纹样）在主流技术类赛事里撞车极少，“方向多元性”直接受益，传播也天生占优。代价是视觉必须走“国潮 + 现代设计”（黑金 / 极简 / 留白），做成年画味就废了；评委不一定认识这个符号，README 和 Demo 开头各加一句英文背景说明即可，成本极低。
- 链上平台的考点、测试网参数、提交材料清单、可直接复用的选题菜单见 `references/黑客松-链上平台要点与提交清单.md`
- **涉链选题先过合规筛（凡"钱在链上转"的一律先判）**：中国境内的红线只有一条实质判据——**那一笔转账的两头是不是"真钱对真钱"**。是 → 资产出境／虚拟货币业务活动，违法；不是（应用内权益、算力、积分，不可转让、不可变现）→ 服务权益转让，属技术演示，可做。参赛姿态守死三条：只用测试网、不面向境内提供任何服务、不发币不募资；**演示里不能出现任何"充值／买币／用人民币换"入口**（有真钱换币，测试网也救不了）。RWA 代币化、稳定币在境内同样被点名禁止，"资产上链变现"类表述也要避开；跨链／桥是技术手段不是产品定位，换形式不改变性质。完整依据（文号、三问自查、把价值载体从货币换成不可变现权益的替换手法、宣传口径）见 `references/涉链项目合规红线（中国境内）.md`
- **别用"换个说法／换个名字"当合规解法**：使用者会当场驳回（"法律可不认这个""人家只看有没有真的把资产转出去"）。要给出他能自己复用的实质判据，并把"改名无用、上主网给真人用就是违法"这条不可逾越的线说死；推理被指出偏差时直接认下、改写，不辩解——他要的是能站住的判断，不是体面的措辞。
- **演示形态优先选"零学习成本"的**：微信红包、抽签、聊天这类人人会用的形态，评委不用解释就懂、传播也占便宜；但必须一眼看出它比原版多了什么内核（如随机数可链上验证、由 AI 自主决定怎么发），否则会被读成抄（"这不就是个红包应用吗"）。
- **美术归使用者，别用手写 SVG 拼人物**：缺美术队友时，**人物/角色立绘绝对不要用几何图形手写 SVG**——拼不出人样（脸是个深色方块、眼睛两个红点、胡须糊成一团、身体一个纯色桶），使用者会直接否掉成品（"这是你说的财神？"），你还会越改越自我说服（盯着自己渲染的图反复微调比例，等于自己给自己打分）。正确做法：①）美术交给使用者——他会主动分工"我负责美术这块，剩下的你做"，并自己出图/找图（给他规格：PNG 透明底优先、1024 以上、竖版、无文字水印、挑可商用的 CC0/公共领域）；②）需要 AI 出图就走 `sensenova-image-and-animation` 那套流程，出图后用 vision 自检再交付，别拿草稿糊人；③）SVG/CSS 只做它擅长的部分——光背、罗盘、几何纹样、动效，图到位后页面配色跟着图走。
- **先定一句品类定位，再谈页面**：对标"桌面宠物"这种句式——一句话说完"是什么 + 长在哪"。定位没聚焦时界面必然退化成一屏东西排队，使用者的反馈会是"布局看着好奇怪""咱们这个没有这么明确的目标"（他会自己指出根因，别急着改 CSS）。做法：把项目收敛成一句品类句，再从三个方向里挑一个——① 品类定位（像"微信红包"那样的物件，如"算力红包"：包的不是钱，是算力）；② 角色定位（像"桌面宠物"那样的对象，如"你的 AI 财神"）；③ 工具定位（给社区/公司发算力激励的工具，最正经但最没劲）。基调通常是"品类当主、角色当壳"。
- **一屏只有一个主角**：定了品类，首屏就放大那个物件，其余（历法、算力、凭证、参数）全部退到第二屏或抽屉里。首屏同时平铺四样东西（形象 + 罗盘 + 信息条 + 按钮）= 眼睛不知道看哪儿，这就是"布局怪"的解药所在。
- **内核必须通用，功能只是入口（比"选品类"更管用的判据）**：使用者会拿别人的方案对照我们——"他的巧妙之处在于内核还是 agent，只是换了张皮"。照这把尺子量自己：**内核 = 工具 + 记忆 + 定时 + 自主循环（通用能力）**，**外壳 = 角色（形象、口吻、仪式感）**，而具体功能（发红包、记账、发券）只是外壳上的一个入口。把某个功能当成项目全部，天花板就封死了，使用者的原话是"咱们这个给功能限制死了"。他因此提出三个定位方向全否时，别再加候选，改架构。
- **改架构时给已有产出按层归位，不推翻重来**：把合约、历法、可验证随机从"功能本体"重新标注成"账本层"，明确告诉使用者哪层不动、哪层加厚（内核加工具/记忆/定时），他才会点头。已跑通的代码一律有位置，这既是省工期，也是让他心里有底。
- **他否掉产出（"看着怪""感觉不太好""不太行"）时先停手**：不要立刻批量做两三个方案让他挑（会被"别，等一下"打断）——他要先说话。听完再动手，他常会自己给出根因（"定位不明确"是最常见的一个）。
- **Demo 前端先按页面类型找参考，别自由发挥**：使用者桌面上已有设计参考库 `我的小项目\VibeCoding设计参考\VibeCoding设计参考清单.txt`（20 个站，按页面类型分组：组件库 Uiverse / ReactBits / React Native Reusables，后台类 Tremor Blocks / TailAdmin，落地页、SaaS 官网、作品集、移动端、电商、服务预约各有对应）。参考站给 AI 的是**结构与组件代码**，字段和文案必须换成使用者行业的（商品购物车 → 设备/机时/结算单），只抄结构不抄内容，否则一眼模板感。
- 环境准备与部署路径见同一份 references（本机实证走的是 Python 那条：`py -3.13 -m venv "D:/venvs/<项目名>"` + `web3` + `py-solc-x`，Foundry 为备选）；编译合约直接跑 `scripts/compile_sol.py`——它把源码从标准输入喂给 solc，绕开 solc 处理不了中文路径这个硬坑。
- **时区**：国外平台（Luma 等）主办的赛事，截止日期可能按非北京时区口径，统一按北京时间提前一天提交，并找官方确认时区口径（使用者也在意这点）。
- **别把自己的产品判断说成比赛要求**：规则原文里没有的东西（"必须能扫码玩""必须做移动端"这类），只能表述成"我的建议"。做法：先把官方手册里的硬性要求逐条抠出来单列一节，再另起一节写自己的建议。使用者会直接质问"这个要求有说吗"——届时能立刻翻回原文、明确改口并收回措辞，比硬撑体面得多；被问住一次就会丢掉他对话语的信任。
- **低成本补齐项，使用者说"都做"就做全**：选题范围要砍到一条闭环，但**交付形态**（PC 宽屏、手机、可安装 PWA、双语材料）属于半天级的补齐项。他说"都做，不能少，评委玩不玩另说，咱们要先做出来"时，把成本与性价比讲一次就够，别再劝退，直接做全——他要的是"先做出来"这件事实。
- **多端交付的实现要点**（一套网页同时喂手机 / PC / 可安装 PWA）见 `references/黑客松-链上平台要点与提交清单.md` 的"多端交付"一节。
- **参考资料类需求**：使用者陆续粘来的参考资源，边收边整理成 txt 放 `我的小项目/<主题>/`，逐条实测链接可用性（用 GET 而非 HEAD 测，否则 403/000 会误判成死链；403 多为反爬，不代表打不开），原始链接被截断的（如 Wix 模板 URL 少了结尾字母）要实测纠正并在文件里标注。
- **中文口号要押韵**：写 slogan 时按韵辙校验——两个分句末字必须同辙（"手/走"由求辙、"蟾/串"言前辙），末字不同辙读起来就断，使用者会直接说"不押韵，换一个"。一次给 4–5 个不同辙的候选，标清辙口和适用场合（主标题 / 副标 / 页面抬头）让他挑，别只给一个。
- **写自己项目的说明别套别人的格式**：照搬队友/群友发来的思路书模板，使用者会觉得别扭（"套用群友那套怪怪的"）。用叙述口气：先一段"这是个什么东西"的场景（谁、什么界面、做了什么、发生了什么），再讲为什么做、怎么运作、技术上不一样的三点、边界与版本、落地排期；编号清单只留在真该列的地方。**连你自己整理的"能力清单/两侧对照"（Agent 侧 / Web3 侧 那种 [1][2][3]）也别摆给他看**——同样会被嫌"生硬""怪怪的"；先用一句"两半"式的话把结构立住（一半是脑子：会看日子、会判断、会说话；另一半是账本：谁领了多少、凭什么、赖不掉），要细节再往下展开。清单是给自己盘进度用的，不是给他看的。
- **文化元素进算法要能解释**：传统符号（干支、时辰、黄历宜忌、方位）一旦说"用它算结果"，就必须给出可复算的输入与规则（块哈希 + 地址 + 干支时辰 → 份额档位），材料里能指着一句公式回答"为什么他这次拿得多"；基调写死为文化娱乐、不承诺收益，别写成算命。角色/形象上传统体系常是"一个班子"（如九路财神：中路正帅 + 八方分职），但短期只做主形象 + 符号化简化（印章盘/方位印记），别画满一整套。
- **文化符号要从装饰升级成"机制"**：把传统历法做进产品的实际使用规则——吉时放开用度、凶时提示"省着点用"并压低额度——比把卦象、纹样画在背景上有说服力得多，而且是别的产品复制不走的差异点；基调仍写死为文化娱乐、不承诺收益。
- **互动/游戏玩法一律不做赌性设计**：不做押注、下注、翻倍、抽奖兑换这类玩法，奖励只能是不可变现的应用内额度（算力/积分/次数）。这既是合规红线（见涉链合规 references），也是平台规则雷区；给玩法时主动把这条红线说在前面，别等使用者问。

### 给零基础使用者讲技术名词（他一定会问）
- 顺序固定：① 先破中文撞车（区块链的"合约"=智能合约，跟期货"合约交易"毫无关系）→ ② 给一个生活比喻（智能合约 = 自动售货机：投币就出货，没有售货员，也不会赖账）→ ③ 落回"咱们这个比赛里它具体是啥"（存证类项目里合约就是那台存证机器）→ ④ 给一条他自己能分辨的判断标准，别让他只记住比喻
- 判断标准要能自己用：例如"下一步是谁决定的"——人决定=普通程序/工具调用，模型自己决定且多轮循环=agent loop。他问"咱们做过吗"时，先跑工具找实物证据再答（本机 `乖乖助手Agent/agent.py` 是真的 tool_calls 循环；台车那套 `ai_agent_core.py` 是离线规则版，不算 loop），别凭印象说"做过"
- 讲完问一句"还有哪句没懂"，别一口气倒术语堆
- 词表（智能合约/L1/HyperSDK/ICM/x402/Gas/agent loop 的白话释义）见 references/黑客松-链上平台要点与提交清单.md

### 代码仓库与 GitHub 协作（他会问"会用 github 协作吗"）
- 先讲原理再动手，按这个顺序：仓库 = 带时间机器的文件夹（记着每次改动是谁、何时、改了哪几行）→ 本地仓库 vs 远程仓库（push/pull）→ 建仓四步 init→add→commit→push → 多人协作 = 各开分支 + 发 PR 汇合 + 合并留痕（不是大家一起改同一个文件）。最好拿个测试文件夹从 init 演示到 push，走一遍他就懂了
- 比赛里仓库的作用：提交材料里那条"代码仓库链接"就是评委看代码、README 和 commit 记录的地方；commit 时间还能证明是赛期做的，不是拿日项目糊弄
- **本机坑（开工前先修）**：git 身份是占位邮箱 `zhender@example.com`（假邮箱，提交不算在他名下），必须换成真邮箱；`gh` CLI 未装，需要就装上（放 D 盘）；GitHub 被墙但本机代理 127.0.0.1:17890 可通
- 他只需要 GitHub 账号 + 完成一次登录/授权；建仓、首次提交、README、分支、PR 都能代劳，但每一步解释给他听，别只给结果

### 赛程后半段（提交之后别散伙）
- 完整时间线通常还有：评审期 → 公布入围（前 10 之类）→ Demo Day → 获奖公布，且**入围公布到 Demo Day 常常只隔 1–2 天**。所以演示录屏和讲解稿在提交阶段就一并做好，一份东西两处用（提交材料本来就要 Demo 视频），别等入围通知再动手。
- 群通知里的时间线**常缺 Demo 环节的形式**：线上还是线下、哪个平台、每人几分钟、要不要出镜，都得单独问主办。手册写"全程线上"时通常只覆盖报名/组队/开发/提交四项，Demo 不在其内——别拿它当 Demo 也线上的依据。
- 多个奖项里**人气奖靠传播**（投票、浏览），是内容/社群能力强的人最容易够到的；把"顺手发一条内容讲自己在做什么"排进节奏，成本低但往往是唯一能稳拿的奖。

### 组队、撞车与转单人（实战教训）
- **别拿队友/群友的方案当自己的作品做**：他把想法发过来，很可能他自己也在参赛——两个作品撞车，评委一眼看出谁像谁的，风险全在使用者这边。合作能谈成可以帮他补短板；一旦没成行，选题必须另起一条线：思路、载体、演示画面都不能与他重合。
- **在别人框架上要有“自己的加码”**：只做对方方案里的执行者等于打下手。上桌时给的是“在他框架上补哪几条”（每条说清为什么值钱、工作量几天、我们交付什么），身份才是并列贡献者。
- **对方不愿组队 / 中途退出时**：不追问原因、不自我贬低，当场转单人方案并**重算范围**——原本他担的模块（合约、美术、前端）现在都落在我们头上，主线必须砍到只剩一条闭环。
- **美术绝不等人**：没有美术队友时，形象先用 SVG/CSS 自己画（矢量、状态可控、体积小、随时能换），AI 出图留作后续替换，别让美术卡住整个进度。
- **图到手后的活儿**：抠底、裁切、按状态换图（正常/开心/吃惊）、配色跟随主图重排页面；他没给图时先做不依赖图的部分（逻辑、材料、自检），别把"等美术"当停工理由。
- **载体优先级：网页 > 桌面客户端**：黑客松 Demo 要能扫码、能发链接、评委手机点开就能玩、录屏也好看；桌面软件要别人装环境才跑得起来，传播和评审两头吃亏（除非选题本身就是桌面场景）。
- **不熟的模块当面对队友直说不会**：主动讲“合约我没做过，这块你来带，我包 AI 逻辑 + 界面 + 材料”，比含糊地什么都应下更能组到队——这一行最怕装懂的人；使用者自己也认这个口径：不会就是不会，直说反而加分。

### 评估使用者/队友提来的方案（逐项三分法）
- 他会把一个整方案（能力清单 + 交互设想）甩过来问“这些咱们能做哪个”。别笼统回“能做”，逐项过完分三类：
  1. **能做且不难**——写清用什么实现，尽量指出本机已有的可复用代码/经验（现成骨架优先于从零写）；
  2. **能做但必须做减法**——点名哪些项在期限内做不完、砍成什么最简版；他自己标了“设计中”的模块一律按最简版处理；
  3. **有风险**——把卡点提前说出来（美术资产、领测试币、私钥存放、需要外部账号/人工介入），并给出卡住时的替代路径。
- 收尾把“锁成哪条闭环”钉死（哪几个功能、剩下的不做），并把工作量落到天。

### 分工（人机）
- 我代劳：合约代码、部署上线、后端数据模拟、网页 Demo、代码仓库+README+架构图、提交材料、Pitch 稿
- 使用者负责：出行业痛点与业务规则（他的核心贡献）、拍板功能范围、出镜讲解与录 Demo 视频、跟主办/Hacker 群沟通（问截止时间、规则澄清）
- 使用者要能当着评委讲清"链上那部分怎么用"——纯代劳会让他答辩时崩，所以边做边给他讲
- 使用者问"你能做好 UI 吗"时如实划边界：**能靠抄成熟结构**（后台抄 TailAdmin/Tremor，组件抄 Uiverse/ReactBits）做出"像上线产品"的样子，不是凭空有审美；同时交代自己看不见渲染结果这条短板并给出解法（本机没装 Chromium 就先 `npx playwright install chromium`，装完自己截图自查再交付）——先说清，别把短板留到交付时才暴露

### 开工后的落地纪律（本机实证）
- **本地链优先，别拿测试网当调试环境**：装 Foundry 的 anvil（单文件二进制，放 D 盘），改一次合约就在本地跑一遍，验证过的代码才上测试网；金额边界、越权、随机这类 bug 全在本地抓。Python 的 eth-tester/py-evm 那条路要 C 编译工具链，本机装不上——别在那上面耗时间。装法与两个关键坑见 `references/黑客松-链上平台要点与提交清单.md`。
- **随机要"可复算"才算亮点**：写成 `keccak(区块随机数, 领取人地址, 池子序号, 领取序号, 档位系数)`，**把全部输入写进事件**，再配一个独立复算脚本，跑一笔真实的链上交易证明结果一致。设计与校验见 `references/链上可验证随机与复算.md`。对外那句话：中心化红包的随机你只能信，链上的随机你能自己验。
- **合约里不放任何转账/转让入口**（ABI 里连 transfer/approve 都没有），并把这条写进测试断言——这是"价值载体不可变现"那条合规边界的技术证据，比口头声明有力。
- **后端改动必须验证是否真生效**：`--reload` 不可全信。改完用一个"只有新代码才会返回的字段"curl 一次；没变就重启服务，别拿旧代码渲染出的界面做判断（会白跑一轮截图和结论）。
- **AI 生成的文案不许出现与系统真实数值冲突的数字**：提示词写死"不要出现任何具体数字/次数"，输出后再正则清一遍，真实数值由系统填。观众和评委最容易一眼看穿的就是"判词说赐你一万次、实际抢到 256 次"这类自相矛盾。
- **界面必须自己先看过再交付**：装 Playwright Chromium 并把 `PLAYWRIGHT_BROWSERS_PATH` 指到 D 盘，用截图脚本抓"首屏 / 点主按钮后的弹层 / 交互完成后"三态，顺带把浏览器 console 报错打出来。
- **进度节奏**：长任务开跑前一句话说明在跑什么，每完成一个可验证节点报一句结果。连续闷头干十几轮不出声，使用者会追问"现在你在跑什么 / 怎么又卡了"——这是他明确表达过的焦虑点，不是单纯催进度（中间短查询仍不必汇报）。
- **他连发多条想法时**：那是他要一口气把设计说完，**别每条都插话**（会打断他），但中间至少留一句"我在听、你接着说"；全程静默他会以为你死了（"你怎么卡了""需要我重新打开吗"）。等他发完再一次性梳理成条目回给他——判断标准：**粘素材（长文、参考清单）要闷头收，口述想法要轻声接**。

### 节奏模板（10 天期）
1. 第1天：定方向 + 环境打通（装工具链、建钱包、领测试币、把最简合约部署上测试网）——“我不会区块链”的心理门槛在这一步就没了。
   **开工先验链上连通性（与选题无关，随时可做）**：`curl -s -X POST -H "Content-Type: application/json" --data '{"jsonrpc":"2.0","method":"eth_chainId","params":[],"id":1}' <测试网RPC>`，返回链 ID 即为通，再打 `eth_blockNumber` 确认在出块；RPC 直连不通就先解决网络，别急着写代码。领测试币这一步**基本都得人工登录，脚本领不到**（build.avax.network 的水龙头要 GitHub 或 Core 钱包账号，faucet.avax.network 要连钱包）——提前把它讲成"需要使用者浏览器操作的一步"，别在脚本里反复重试；备选是让使用者在赛事/社区群里求一点测试币（顺手露个脸，后面拉人气票有用）。区块浏览器对脚本返回 403 属反爬，浏览器里正常。
2. 第2-3天：合约核心逻辑
3. 第4-6天：数据模拟端 + 前端 Demo，能点能看
4. 第7-8天：部署测试网、全流程跑通、录 Demo 视频
5. 第9天：代码仓库 + README + 架构图 + 提交材料
6. 第10天：提前提交（不卡截止）

## 常见注意

1. **年龄和组别限制要提前确认** — 如45周岁以下、种子组不需要公司注册等
2. **报名渠道** — 地市推荐 vs 省直单位推荐，要提前弄清
3. **团队人数** — 以官方规则为准：2026河南"豫你携手·创赢未来"大赛官方=团队总人数不多于5人（45周岁以下）；使用者备战计划xlsx里自拟的"团队角色5~7人"是建议不是规则，写BP/报名材料时别照搬（官方信息全文见 references/2026-河南青年科技创新大赛详情.md，含报名系统/电话/邮箱）
4. **不要替用户决定项目方向** — 给几个选项让用户选，用户说要先摸底就先摸底
5. **鼓励先做落地产品再参赛** — 用户偏好先出东西再比赛，遵循这个节奏
6. **文档格式** — 用户要求txt或docx，不要md
