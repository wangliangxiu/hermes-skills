# 多平台内容分发的接口现实（评估「矩阵自动化」类承诺时用）

用途：对方方案里出现「六平台一键分发」「一条内容自动发全网」「日均确认 <15 分钟」「1 人 + Agent 运营六个平台」这类承诺时，用本文对照，判断可行性并改写里程碑。

**接口政策会变，且按账号主体不同而不同。落地前必须用对方实际账号实测（能不能入驻、能不能拿到发布权限），不要凭记忆下结论。**

## 逐平台判断要点

| 平台 | 发布类能力的现实 | 对方案的结论 |
|---|---|---|
| 抖音 | 开放平台入驻主体要求企业 / 个体工商户，需主体认证与应用审核；发布类能力挂在企业号等开放能力上 | 个人主体账号做不了自动发布，必须是对方公司/个体户主体 |
| 快手 | 同为视频平台，开放能力面向机构/服务商，普通账号发布不成体系 | 默认按「生成 + 人工搬运」排期 |
| 微博 | 开放平台需企业/开发者应用审核，个人拿不到写权限，发布类能力不面向普通用户 | 「自动发微博」不成立，按人工搬运 |
| 小红书 | 开放平台面向聚光、蒲公英、私信工具、千帆推广等商业化 API；普通笔记发布不是公开能力 | 市面上「一键发布」工具多为逆向接口或客户端脚本，正是方案里自己划的红线 |
| 知乎 | 开放平台偏数据方向（数据开放平台、REST/MCP），发布能力不对普通开发者开放 | 「近乎全自动」不成立，按「生成 + 人工发」 |
| B 站 | 开放平台有视频上传、稿件管理、创作者数据能力，需开发者入驻与审核 | 能力存在但门槛在入驻审核，不是装上就能用 |
| 公众号 | 草稿箱 / 发布接口有公开文档，权限与账号认证主体类型挂钩 | 这是最可能先跑通的平台，但必须拿实际账号实测申请权限 |
| TTS / ASR | 采购 API 一天能接 | 接口好接，但「质量能对外发」的成片流水线是长期工程，不要承诺短期交付 |

## 回答「发布这一环能不能自动」的三档口径

对方问「能不能自动发出去」，不要给一个「能/不能」，按三档分开说：

1. **全自动无人值守发布：做不到。** 上述平台没有面向普通开发者的公开发布接口，谁说能做谁在骗人。
2. **半自动（浏览器自动打开编辑器、把图文填进去，最后一步人点发布）：技术上可行，但属模拟客户端操作**，平台判为机器行为会限流甚至封号，且正是对方文档自己划的红线。可以写进选项，但**不作默认方案**，要做先书面告知风险。
3. **人工搬运（把成品打成发布包：按平台分好文件夹的文案 + 图，手机上复制粘贴）：现阶段默认方案。** 安全，每次多花几分钟。

**唯一例外**：微信公众号草稿箱接口是公开能力，可做到「自动进草稿箱、人点发布」，前提是账号有认证主体。

配套口径：

- **缺的是资质不是技术**：平台开发者权限（企业主体＋审核）、账号认证主体、支付商户号——对方出不来，就只能停在人工档。写进合同「需要对方出人出资质」。
- **回答的落点用「八成自动化」**：找信息 → 整理 → 改写成各平台版本 → 配图 → 打包，全链无人；最后一环留人。八成无人已足够让客户觉得值，因为那八成是他一天干不完的活。

## n8n 的许可边界（易被忽略）

n8n 采用 Sustainable Use License：允许内部业务用途，**不允许把 n8n 本身作为服务转售或托管**。

因此当方案出现「承接外部订单」「交付完整系统源码」时：可交付的只有工作流 JSON 与配置，不是「系统源码」；若真要对外卖系统/托管给客户，许可边界要另找方案。

## 写进回信的口径

- 「六平台一键分发、日均确认 <15 分钟」在现有平台生态下不成立 → 现实落法是方案里的 C 级：生成 + 人工搬运（人工确认点保留）。
- 里程碑若绑定了做不到的自动化目标（如「第 10 周末六平台闭环」），要求**按 C 级口径改写后再开工**，否则验收注定扯皮。
- 先行平台选接口最成熟的两个（公众号、B 站/知乎的生成侧），先跑通一个再复制。
