# 外部方案可行性评审 + 对外回复

适用：用户把一份别人给的方案/指令书/合作材料丢过来，问“这个可操作性如何”“咱能做多少”“帮我回复一下”。
交付两样：一份评估 txt（放 `我的小项目/<任务名>/`）+ 需要时一封可直接发出的回信稿（单独文件）。

## 一、先读全，再说话

- 整篇读完再下判断，不看目录/摘要/开头就评。HTML 先转纯文本再读（正则去标签，转完删临时文件）。
- 记三样硬信息：谁写的（各方角色分工）、承诺了什么（工期/阶段/交付物/验收标准）、要你承担什么。

## 二、找文档自己的矛盾（最值钱的一段）

多版迭代的方案，矛盾就藏在这几处，逐条给出行号/章节位置：

- **验收标准 vs 阶段边界**：验收表里混进了下一阶段才做的东西（例：阶段一写“不做自动分发”，验收表却写“可自动分发”）→ 拿这条验收永远过不了。
- **时间口径多套并存**：同一件事在不同章节写了三四个完成时间。
- **交付物 vs 自己立的原则**：主张“优先采购成熟方案”，又要求交付“完整系统源码”——采购来的 SaaS 交不出源码。
- **第三方许可**：拿别人的开源组件当交付物前先看许可证（Sustainable Use License 类只允许内部业务使用，不能转售/托管）。
- **角色被缩小、责任没缩**：工作量被重新定义成“接入配置”，验收力度还是按“系统集成商”写的。
- **版本病**：版本号反复迭代、通篇“勘误/口径/写死”。判断对方靠不靠谱看事实（书出了没、账号多少粉、卖了多单），不看改了多少版。
- **钱与责任空白**：工期、需求项、验收都写了，报酬/费用/产权/退出/账号实名一字不提——这是常态不是疏忽，列为必须先谈项。

## 三、能力清单按快/中/难分档（回答“咱能做多少”）

把对方要的东西拆成条目，逐条落档，每条给工时与前提：

- **快**（天级到一周，能独立交付）：基础设施、建库、编排工具、接口层、落地页、看板、SaaS 选型开通——凡是“配置+接入”都在这档。
- **中**（周级到两三周，能做但会反复）：中台、检索/关联、调度底座、数据回流。质量型目标（文风一致、成片质量）不给工期承诺。
- **难**（基本做不到文档写的样子）：需要平台官方写接口的（多平台自动发布）、需要跳行资源的（外贸的品类/资质/资金）、需要无人值守保证质量的。

分档判据是**约束在哪**：工时约束 → 快/中；平台权限或资源约束 → 难。后者不是加班能解决的，先核实官方文档或实测，再决定要不要写进承诺。

## 四、必问条款清单（开工前对齐）

1. 投入方式（全职/兼职/每周时间）2. 报酬与结算节点 3. 费用谁出（服务器/SaaS/API/账号）4. 范围写死（超出怎么算）5. 验收方式（谁签字、按哪版表格）6. 知识产权归属 7. 账号实名与责任划分（封号/违规）8. 变更与终止结算。

## 五、交付与口径（使用者偏好，必遵）

- 输出用 **txt**（不用 md），放 `我的小项目/<任务名>/`，回复里给绝对路径。
- **不会的事直接写“不会”**，不包装成“分工不合算/这块更适合别人”；不替对方做内容与商务决策。
- 对外材料**不做竞品对比**板块、不碰瓷大厂；目标客户可点名头部；数据用自身数据。
- 平台接口政策、合规、税务、牌照类结论，写清“这条我核实过”还是“需以官方文档实测为准”，不凭记忆断言；能实测就先实测。
- 回信稿要有点名的问题（按上文二、三节逐条列）和下一步（要详版、要实际账号做权限实测、先做一件 3 天可交付的小活验一次）。

## 六、交付物分两套：内部件与对外件（铁律）

同一件事落成两类文件，物理分开，别混：

- **内部件**（自己看）：文件名带「内部」；首行写明「本件是内部记录，不给对方看」。判断、顾虑、报价策略、对对方的评价、下一步要谈的钱，全放这里。
- **对外件**（可发人）：文件名带「给XX先生」或「对外」。**默认不写使用者的姓名、电话、微信、邮箱**——使用者明确要求过；要署名先问再写。
- 对外件里**绝不出现内部判断**：打样要不要收费、我方顾虑、对对方背景或能力的评价、我方做不到的能力，一个字都不写。使用者说过「别说这些」，就从内部件里也一并拿掉，只留一句通用原则（如「对外一律用真实口径，不替使用者编经历」）。
- 使用者是口述给材料的：**原话落盘、一字不改**；我自己的推断单独标「（判断，请使用者核实）」，不混进他的话里。每条结论标清来源：【他说的】/【使用者说】/【Hermes 判断】。

## 七、对接记录是活文件

- 建一份 `<对象>对接记录.txt` 放项目目录，固定结构：他讲的（编号）/ 我方判断要收紧的 / 下次谈之前要问的 / 今天定下来的 / 备忘。
- 每谈完一次**用 patch 往后面追加**，不改前面（write_file 是整体覆盖，会吃掉历史）。
- 下次谈之前让使用者先扫「要问的清单」和「必须说清的前提」，上回到哪一目了然。

## 八、对外说明书/方案书写法

- 拿得到对方文档时**照对方的形态做**（他给 HTML 就出 HTML），两份放一起像一套；源文件找不到就说明一声，按同类文档风格出：单文件 HTML + 内嵌 CSS、A4 纸宽、可打印、无外部依赖。
- 交付前自己先跑一遍：结构自检（数 `<h2>`／`<table>`、看结尾标签完整）+ 打开看渲染。渲染验证卡住别耗着，直接把文件用系统默认程序打开给使用者看（Windows git-bash：`explorer.exe "C:\路径\文件.html"`），使用者的眼睛比截图快。
- 对外材料先划边界，把扯皮点提前写死：谁出账号与密钥、API 费用谁承担、哪一步必须人点、不接哪些活（不代运营／不代写／不承诺涨粉收益）。写在对外件里，使用者谈的时候照着念就行。
- 打样、样板是可复制资产：对方要「先做个样」时把条件一起摆上桌——样算不算活儿（给不给钱、几天交）、样板他用在什么范围（只演示／当教材／转卖）、署名挂不挂我方的名。
- 合作方的客户是散户时，「卖模式」这类生意有夸大宣传与退款纠纷风险：责任划在对方那边，我方名字不挂在此类背书材料上。

## Pitfalls

- 文档写得专业 ≠ 能落地：专业的是格式和口径，落地看的是权限、资源、资金。
- 里程碑绑死了做不到的目标 → 先重谈里程碑口径再谈开工，否则验收必吵架。
- 别把“版本多、条款细”读成“准备充分”，也别把没写钱读成“对方大方”。
- 评估里出现“顺手也能做 X”这类自我加码 → 先问有没有人付这笔钱。
- 内部讨论（打样给不给钱、我方顾虑）写进对外件 = 事故：这份东西使用者是要发出去的，等于把我方的底牌摆在对方桌上。
- 我的推断不标注，使用者就分不清哪句是他说的、哪句是我加的，对外转述必然失真。
- 交付形态别自己定死：能做多少写多少档（全自动／半自动／人工确认／定制），把做不到的写清楚，比全写成“能”安全——写满了后面全是扯皮。
