# 口述经验 → 技能（蒸馏流程）

适用：用户说"把我在某行干过的东西做成技能""社区让我交个技能"这种——手里只有人的经验，没有现成文档。

**核心判断**：这类任务的瓶颈不是写代码，是隐性经验显性化。SKILL.md 是纯文本规则文件，知识型技能不需要一行代码；能写公文、能写方案的人就具备全部能力。会卡住的地方是本人"不知道自己知道什么"，所以流程从选题标准和访谈设计开始，而不是从动笔开始。

## 零、选题标准（先定死，否则后面全白干）

三条都要满足：
1. **本人张口就能说出细节**（有场面、有例子、有自己的判断）；
2. **别人拿去能用**（不依赖他所在地区/单位/项目的特殊前提）；
3. **不需要写代码**。

不要用"传播力/爆款/容易被转发"当选题标准——志愿性质的社区贡献里这个标准会让作者反感，也选不出真东西。

两类典型反例，先自己排掉：
- **地区性条款清单**（各地要求不一样，做成通用清单就是误导别人）；
- **本人答不上来的领域**（硬写等于编，必须整套砍掉）。

操作姿势：**先广撒网提问，答得最顺的板块就是题目**。不要先定题再找料。

## 一、访谈：一次一问，边问边落盘

- 开工前让用户挑方式："你自己先讲一段我拆" 还是 "我逐条问你逐条答"。他通常挑更省事的那条。
- **一次只问一个问题**，最多带一个补充追问；每个问题后面给一句提示或两个候选方向，降低启动成本。
- **"确认-纠正"式提问优于开放式**：先把我提炼出的规则/复述抛给他（"我理解是 A，对吗？还是还有更细的判法？"），他只需点头或改一处，比从零组织语言省力得多。
- **不要用选项表单征求意见**：用户在 CLI 下会误提交（会反问"我还没选呢"），改用纯文本编号（1/2/3）让他回一个数字。
- **每答完一条立刻追加到项目文件夹里的 `访谈素材.txt`**：保留原始口语、不润色，每条末尾加一行【提炼】写我读出的规则。会话被压缩或中断时素材不会丢，也方便最后成稿。
- 他给出否证（"有过但很少""基本上没有那种情况"）时，**立刻撤回对应设想**，不要继续把它当卖点写进技能。

## 二、绝不自造前提

用户没说过的项目类型、岗位、工序、年份、单位，一律不写进素材，也不拿它当提问前提。
行业经验里最容易被想当然的就是"他大概干过 X"——这类推断一旦被本人纠正，整段叙事都要推倒。
答上来跟我记的不一致时：当场认错、改素材文件、明确说这条以后不问了；不要含糊过去。

## 三、素材以实物为准

用户愿意给真实样本（标书、方案、台账、截图）时优先读实物，比追问更高效：
- 指定专属文件夹让他放（`<项目文件夹>/样本/`），并先讲清隐私边界：**只读与技能相关的那部分**（结构、判断、话术），跳过敏感内容（报价、证件、单位抬头、人名）；社区版一律去单位名、人名、具体里程。
- 能直接读 docx / pdf / txt；`.wps`、扫描件图片要先请他另存为 docx/pdf。
- 读完对照他口头说的，差异处往往是他自己都没意识到的套路，价值最高，值得单独追问。

## 四、成稿结构

1. **元数据**：description 第一句（约 57 字内）讲清"什么时候该用它"，这比正文更影响触发命中。
2. **现实约束放最前面**（周期、人手、甲方给的时间），它决定整篇的取舍原则——周期紧的行业，第一原则是"时间不够时先保什么、哪些绝不能省"，不是"怎么做到完美"。
3. **主流程分步**，每步写清判断依据（谁给的资料、看什么定什么）。
4. **清单与判断规则**（什么该出现、什么不该出现）。
5. **句式模板**（能直接抄的开头、结尾、过渡）。
6. **常见坑与反例**，必须来自本人经历；"这几句话最容易被挑""这个签字顺序错了就白签"这种才有说服力，通用最佳实践一填就露馅。
7. **复用与改写的分界线**（哪部分能照搬、哪部分必须按当次项目重写）。

## 五、定稿流程

草稿 → 本人审改（问"哪里不像我说的"，别问"你觉得好不好"）→ 本机实测（拿真实场景跑一遍，看输出像不像真干这行的人写的，不像就改到像）→ 去私人化后再交社区。

**交付前必须核实**：写完文件先 `ls` 确认路径存在，再向用户报路径；没写成的不许说成写好了（曾把还没生成的提纲说成"已经写出来了"并编了个路径，被当场问住）。
