# 外部合作方案评估与回信

## 何时用

- 对方（潜在合作方、客户、雇主、团队）发来方案书 / 技术实施指令书 / BP / 实施计划，使用者问「这个可操作性如何」「咱能做多少」「哪些快哪些难」「要不要合作」
- 需要以我方名义回一封信、一段话给发方案的人

## 步骤

### 1. 读全文，不要只读摘要和目录

大 HTML 先转纯文本再读：HTML 里表格与章节挤成乱行，直接读会漏内容和矛盾点。转换后按行号分段读（1400 行文本约 4 次 read_file）。

Python 一行式转法：去 `<style>/<script>` → `<br>` 换行 → `</p|div|h1..h4|li|tr|section>` 换行 → `<td>` 换 `"| "` → 去掉剩余标签 → `html.unescape` → 合并多余空行，写到临时 txt。

临时产物放任务文件夹或运行目录，读完立即删除，不在桌面留痕。

### 2. 判可操作性，只输出三档（用户要的就是这三档）

- **A 档 · 快**：天级到一周、一个人能独立交付并看到东西的
- **B 档 · 中**：周级到两三周、能做出来但会反复的
- **C 档 · 做不到 / 现阶段做不到**：直说，每条附一条机制层面的原因（资质、平台接口开放范围、许可、外部顾问刚需）

每档逐条对应到对方文档里的条目编号（例如「对应自建清单第 1/2/5 项、采购 A 组、E 组」），回信里「范围写死」才有依据。

### 3. 找文档硬伤（最有价值的部分）

使用者明确要「找漏洞补缺失，不要只夸」，这一节比工期估算更值钱。必查七类：

1. **自相矛盾**：同一件事在两章口径相反（如「某阶段不建 X、放下一阶段」vs 验收表里就有 X）→ 拿这条验收永远过不了，必须要求二选一定稿
2. **时间口径多版本并存**：第 N 周完成 / 第一阶段 X 天 / 里程碑节点 各一套 → 要求合并为一套
3. **交付物与自己的原则冲突**：一边写「采购优先、不自造轮子」，一边交付物写「完整系统源码 Git 仓库」——买来的 SaaS 交不出源码；第三方组件（n8n 等）有许可限制
4. **缺章 / 版本病**：目录列了正文没有的章节（说明是抽出来的简版，要看详版）；V22→V2901 式多轮改版说明前期在打磨文档不在搭系统
5. **实名主体与责任空白**：平台账号用谁的身份证/营业执照注册、封号与内容违规谁担
6. **预算与报酬空白**：服务器/SaaS/API 订阅谁出钱、这段时间有无报酬，一句没写
7. **角色被自我收缩但责任没缩**：文档把技术角色从「造系统」改成「采购接入+配置」，工作量小了，但验收项和里程碑还是按系统集成商力度写的

### 4. 合作条款空白清单（开工前必须问清）

投入方式（全职/兼职/时段）、报酬与结算节点、费用谁出与预算、范围写死（以对方文档条目为准）、验收方式与签字人、知识产权归属、账号实名与责任划分、变更与终止结算。

单列一节「**需要您方出人出资质的部分**」：营业执照、对公账户、支付商户号、平台认证主体、存量素材整理——这些不出，采购接入类工作一半落不了地，是真实进度卡点（不是技术风险）。

### 5. 出回信，结构固定

对方文档判断 → 技术侧能做到什么程度（A/B/C 三档）→ 需要先定清的地方 → 需要您方出人出资质的部分 → 合作条款先谈清 → 建议的下一步 → 落款含联系方式。

模板见 `templates/collaboration-reply-template.md`。结尾给使用者「可调的两个地方，你定」（例如条款清单要不要放进初次回信、落款身份怎么写），让使用者拍板。

## 交付物分层：内部件 / 对外件（必守）

同一单合作会同时产出两类文件，混了会出事，先分层再落笔：

- **内部件**（自己看，不给对方）：可操作性评估、对接记录、框架与方案稿。里面写的是判断、怀疑、风险盘算、我方底线。
- **对外件**（可发人）：回信稿、对接包（含样例与目录说明）。只出现能交付的口径与我方正式的方案。

规则：

- **内部判断一句都不许进对外件**：对对方可靠度的判断、我方对合作风险的盘算、对方对我方背景/资历的误读与其纠正——这些只写进内部件。使用者会明确要求「生成对接文件时别说这些」。
- **文件名带标记区分**：内部件带「内部」，对外件带「给<对方>」或「对外」；使用者一眼能分清，不会发错。内部件正文开头再写一行「本件是内部记录，不给对方看」。
- 交文件前报一句「这份是内部的/对外的」，使用者点头再往下走。
- **对接记录是活文件**：每次谈完使用者会口述，整理成《对接记录》放任务文件夹；下次谈之前扫一眼就知道上回到哪。追加用 patch，不用 write_file（后者整体覆盖会吃掉前面内容）。记录里把「他说的」与「我的判断（待使用者核实）」分开标。

## 用户偏好（铁律）

- **不会的直接写「不会」**，不包装成「分工不合算」之类话术；做不到的部分要写明「这是真的做不到，不是保留条件」。
- **不做对方的执行方**：回信要有我方自己的方案、范围与结算口径，不做无条件接活的口头承诺。
- **先小活验证**：建议先用「3 天可交付的小活 + 按小活结一次账」验证合作，再谈长期全包；不一次性承诺「90-120 天全包」。
- **对外材料不写工作年限**（写「多年施工经验」），不编数据；对方文档里没有的存量事实（出版、粉丝、销量）不替对方假设，写「需现场核实」。
- **输出 txt 不是 md**，放在 `桌面\我的小项目\<任务名>\`。

## 常见坑

- **别用版本号和文档打磨程度判断对方靠谱度**：看存量事实——书出了没有、账号多少粉、课程卖了几单、现有团队几人。一小时的现场核实比读六遍指令书有用；直接建议使用者要一次「现场打开后台核实」。
- **别被「合伙人」名义套住**：对方自己把技术角色写成「采购接入+配置」时，责任别跟着背成系统集成商；按接入/运维的市场价谈工时或项目结算，不接受「挂合伙人名义干运维活还不拿钱」。
- **平台接口现实先摆出来再谈工期**：承诺的「多平台一键分发、日均确认 <15 分钟」通常卡在平台主体资质与接口开放范围，不卡在加班。详见 `references/platform-publishing-api-reality.md`
- **简版必须换详版**：从大稿抽出的简版缺的正是工程细节与验收清单，看简版报工期等于蒙，要主动索要详版章节。
- **平台权限的结论要当场实测**：本类判断涉及第三方 API 政策，回信里写「需用实际账号实测」，不要凭记忆断言某平台一定能或一定不能。
- **评估之后要落地成产品时**（打样、装到客户机器上、卖技能包更新、划定制与售后边界、给客户画的交付框架骨架）：口径、许可与框架事实见 `agent-product-packaging` 技能（含 `references/hermes-packaging-and-license.md`、`references/client-delivery-framework.md`）。
